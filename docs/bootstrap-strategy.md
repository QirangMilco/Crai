# Crai 开发启动策略 (Bootstrap Strategy)

## 1. 目标

Crai 的目标不是一开始就完全自给自足，而是先依赖外部 coding 工具完成冷启动，再逐步把开发、验证、追踪和迭代能力迁移到自身系统内。

这些能力属于通用开发能力，Crai 自身只是它的第一个用户。

## 2. 核心原则

### 2.1 核心保持干净

核心包只保留与运行时执行直接相关的能力，不承载项目管理、开发辅助等产品化功能。

### 2.2 开发能力在扩展与应用层

凡是与"帮助开发工作"直接相关的能力，优先放在：
- 扩展层 (extension)
- 应用层 (app layer)
- `packages/devtools`

而不是放进 `@crai/core`。

### 2.3 核心只提供必要钩子

核心可以提供事件、钩子、注册表、命令契约和抽象接口，但不内建自动拆任务器、代码补丁编排器、仓库巡检器等产品化功能。

### 2.4 安全是不可协商的核心关注点

工具安全性不应推迟到后续阶段。安全是 runtime 的执行契约。详见 [security-model.md](security-model.md)。

## 3. 推荐落位规则

| 层 | 内容 |
|----|------|
| `@crai/core` | 运行时必需抽象、实体契约、events/hooks/adapters、安全类型 |
| `@crai/runtime` | 执行循环、状态调度、扩展生命周期、安全检查 |
| extension / app | 开发工作流、任务拆解、repo 分析、测试编排 |

## 4. 判断标准

如果一个功能的目标是"让开发工作更高效"，先问三个问题：

1. 它是否直接影响 runtime loop 的正确性？
2. 如果不是，它是否只是开发辅助能力？
3. 如果是，是否可以放到扩展或应用层？

若答案依次是：否、是、是，则不进 core。
